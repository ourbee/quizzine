# SPEC — Allotted tests (one student, one question)

Status: **built and shipped, 2026-08-30**, in five commits following §10's build
order. Companion fixes bundled: a sign-out button on every teacher page (§8) and
a redesign of the `/teacher/new` intake step (§9).

**What changed against this spec while building.** Recorded here because the
code is the authority now and the differences are the interesting part:

- **The quiz is born closed, not merely blocked from opening.** `POST
  /api/quizzes` sets `accepting = false` for an allotted quiz, so the window
  between publishing and attaching a roster is never one where a student can
  arrive to find nothing waiting. An edit that orphans a roll closes the quiz
  again and says so.
- **`/api/attempts/lookup` was not built.** The start route took the whole job:
  it verifies the roll, deals the hand, stores it on the attempt and returns
  the sanitized questions in one call — the two-step form is a client concern,
  and a second endpoint would have been a second place to get the gating wrong.
  `GET /api/attempts/allotted` exists instead, for recovering a hand after a
  reload, mirroring the MST stage route.
- **The marking screen needed more than a default view.** Both views filter to
  the cells that exist, a student's total is computed over their own hand, and
  the package scope labels describe the allotted shape ("4 students, each with
  their own question") rather than a grid that is mostly empty.
- **The intake redesign kept a paste box in the upload card**, reached by an
  "or paste it as text instead" link, exactly as §9b's closing note allowed.

---

## 1. What this is

A new quiz mode where every student gets a **different question** — not a
different shuffle, a different question altogether. The teacher supplies a
bank of questions (typically generated by the Quizzine Marker project) and a
roster of roll numbers for one semester. Quizzine deals one question (or a
fixed few) to each roll. The student opens the link, enters their roll
number, sees *their* question, types their name, answers, submits. Marking —
including the copy-package / paste-back AI pass — continues to work.

Working name in the UI: **“Allotted test”**. Internal flag: `allotMode`.

---

## 2. Design decisions (settled)

1. **The identifier is roll + semester, but the semester is fixed by the
   teacher.** The roster belongs to one semester, so the student start form
   shows the semester as a locked label, not a dropdown. One less thing to
   mistype; the duplicate-attempt check still keys on `rollNorm + semester`
   exactly as today.
2. **Unknown roll = polite refusal.** A roll not on the roster gets
   “Your roll number isn’t on the list for this test — check with your
   teacher.” No fallback question in v1. (A fallback invites the whole class
   to try random rolls to browse the bank.)
3. **The bank never reaches the browser.** `/api/public/[slug]` must return
   *no questions* when `allotMode` is on — metadata only. The allotted
   question(s) come back from `/api/attempts/start` after the roll is
   verified. This is the MST precedent (see the comment in
   `app/api/public/[slug]/route.ts`) applied again.
4. **Allotment is stored on the quiz, not in `settings`.** `settings` leaks
   partially to the public route; the roster (and the roll→question map) is
   teacher-private. New jsonb column, same `ALTER TABLE IF NOT EXISTS` idiom
   as `mst`, `marking`, `telemetry`.
5. **Deterministic dealing, teacher-editable.** Auto-assign uses
   `seededShuffle` (`lib/normalize.ts`) over the bank with a stored seed, so
   “re-deal” is one click and the mapping is reproducible. The teacher can
   then override any single cell by hand; overrides survive a re-deal only
   if we make re-deal explicit (“this discards your manual changes” confirm).
6. **More rolls than questions is allowed, with a visible warning.** The
   deal cycles the bank (“48 rolls, 30 questions — 18 questions used
   twice”). More questions than rolls just leaves the surplus unused.
7. **`questionsPerStudent` is 1 by default but the model supports k.** The
   map is roll → `qids[]` from day one; the UI exposes a small number input.
   Writing tests will mostly use 1; grammar drills may want 2–3.
8. **Mutually exclusive with** `mstMode`, `groupMode`, and peer grading
   (`gradingMode: "peer"`). Compatible with: `graded`, `survey`, `rubric`
   grading; `examMode`; timers; `closesAt`; `pasteGuard`; word limits.
   `shuffleQuestions`/`shuffleOptions` become irrelevant (still fine to
   leave on — shuffling one question is a no-op).
9. **Max score is per-attempt**, which the schema already supports
   (`attempts.max_score`); each student’s max is the points of *their*
   question(s). Reports must never assume a common maximum — the reports
   code already handles per-attempt max because of MST.

## 3. Data model

```
-- quizzes
ALTER TABLE quizzes ADD COLUMN IF NOT EXISTS allotment jsonb;

-- attempts: which questions this attempt was dealt (like `mst`)
ALTER TABLE attempts ADD COLUMN IF NOT EXISTS allotted jsonb;  -- string[] of qids
```

```ts
// lib/allot.ts
export interface AllotmentEntry {
  roll: string;        // normalized via normRoll
  qids: string[];      // dealt questions, order preserved
  manual?: boolean;    // true when the teacher overrode the deal
}
export interface Allotment {
  semester: number;    // the whole roster's semester
  perStudent: number;  // questions per student, default 1
  seed: string;        // re-deal reproducibility
  entries: AllotmentEntry[];
}
```

`QuizSettings` gains `allotMode?: boolean` (absent = off, the usual
back-compat rule). The `Allotment` itself never rides in `settings`.

`lib/allot.ts` owns: normalization (`normalizeAllotment`), the dealer
(`dealAllotment(bank, rolls, perStudent, seed)`), coverage stats
(rolls without questions, questions used n times, rolls submitted vs not),
and the roster parser (paste text → rolls; digits-only rule reused from
the start route).

## 4. Teacher side

### 4a. Creating the bank — `/teacher/new`

A **mode picker** at the top of the existing new-quiz page, two cards:

> **Same paper for everyone** (default — today's behaviour)
> **Allotted test** — each student gets their own question from the bank

Choosing “Allotted test” changes nothing about how questions are entered —
the same paste box, the same parsers (`parsePastedText`, `parseJsonText`,
`parseMarkdownText`, xlsx). The bank *is* a question list. What changes:

- The **AI prompt** button copies an allotted-test variant:
  `lib/aiprompt.ts` gains an `allotSection()` appended to `AI_PROMPT` —
  “generate N distinct questions of comparable difficulty on the same
  topic, one will be dealt to each student” — same output format, so no
  new parser. (Rule from NEXT-SESSION.md applies: the prompt teaches
  intent; the format spec stays single-sourced.)
- After save, the teacher lands on the edit page with the **Allotment
  panel** open and a nudge: “Now attach your class roster.”

### 4b. The Allotment panel — `/teacher/quiz/[id]/edit`

A collapsible panel (visible only when `allotMode`), three zones top to
bottom:

1. **Roster in.** Semester select (one value for all) + a textarea for roll
   numbers (one per line, or comma/space separated — the parser is
   forgiving) + an upload button accepting .xlsx/.csv (first column, or a
   column headed “roll”; reuse the workbook plumbing the importer already
   has). Shows a live count: “42 roll numbers · Semester 3”.
2. **Deal.** “Questions per student” (default 1) and a **Deal questions**
   button. Warnings render here: bank-smaller-than-roster cycling note,
   duplicate rolls in the paste (deduped, listed).
3. **The register.** A table: Roll · Question(s) dealt (first ~80 chars of
   each stem) · a per-row “change” control (dropdown over the bank) for
   manual overrides, which mark the row `manual`. **Re-deal** repeats the
   seeded shuffle with a fresh seed after a confirm that names how many
   manual rows it will discard. This table is the teacher’s source of truth
   — printable, scannable, the same register idiom the quiz detail page
   already uses for responses.

Saving the quiz saves the allotment with it (one PUT, the edit page’s
existing save path, now carrying `allotment` alongside questions/settings).

Guardrails in `lib/validate.ts` / the quizzes route: refuse to open an
allotted quiz for responses (`accepting`) while any roster roll has no
dealt question, or while the roster is empty — with a message saying
exactly that.

### 4c. Quiz detail — `/teacher/quiz/[id]`

- Card badge and header line: “Allotted · Sem 3 · 42 on roster”.
- The responses register gains a **coverage strip**: 31 of 42 submitted,
  and a “Not yet submitted” expando listing the missing rolls — the roster
  finally tells us who *hasn’t* turned up, which no current mode can know.
- Each response row shows the stem of the question that student was dealt.

## 5. Student side — `/q/[slug]`

Two-step start, replacing the current one-shot form **only when
`allotMode`** (everything else keeps today’s flow):

1. **Who are you.** Roll number field + the semester shown as a fixed chip
   (“Semester 3”). One button: **Find my question**. Server verifies the
   roll against the roster (`POST /api/attempts/lookup` or a mode of the
   start route — see 6) and returns the allotted question(s), sanitized
   exactly like the public route sanitizes (no `correct`, no feedback).
   Unknown roll → the refusal message from §2.2, inline, non-scary.
2. **Confirm and sit.** “Roll 17 — Semester 3” shown as a locked header
   with a “not you?” link back; **name field** (they type it manually, per
   the design); then the normal quiz surface — same question renderer,
   passage blocks, word-limit counter, exam mode shell if enabled, timers.
   For `perStudent > 1` the questions just stack as usual.

Submission, result, and review pages need only this: the review payload’s
`questions` array is the attempt’s allotted questions, not the quiz’s bank
(the per-question results already ride per attempt, so `/q/[slug]/result`
and `/review` render unchanged once fed the right list).

## 6. API changes

| Route | Change |
| --- | --- |
| `GET /api/public/[slug]` | When `allotMode`: return metadata + settings as now, but `questions: []` and an `allotted: true` marker so the page renders the two-step form. |
| `POST /api/attempts/start` | Accepts `{slug, roll}` for allotted quizzes (name comes at submit — or at start, see note). Verifies roll ∈ roster + semester from the allotment; duplicate check as today; stores `allotted` qids on the attempt; responds with the sanitized allotted questions (MST-style: the server deals, the client receives only its share). |
| `POST /api/attempts/submit` | Score against the attempt’s `allotted` qids only; `max_score` from those questions; reject answers to qids not allotted to this attempt. |
| `GET /api/result` | Build `ReviewPayload.questions` from the attempt’s allotted qids. |
| `PUT /api/quizzes/[id]` | Accept + validate `allotment`; enforce the §4b guardrails. |
| `GET /api/quizzes/[id]` (teacher) | Include `allotment` so the edit page and mark page can render the register. |

Note on the name: collecting name at step 2 keeps the lookup zero-friction
and means an abandoned lookup leaves a nameless in-progress attempt — the
same abandonment shape MST attempts already have. Alternatively start the
attempt only at submit; but the timer/deadline machinery hangs off
`attempts/start`, so keep start-at-lookup and pass the name with the first
save/submit.

## 7. Marking and the Marker

- **Packages need (almost) nothing.** `buildPackage` takes the question
  list and an `answer(attemptId, qid)` fn, and **drops blank cells before
  building parts** — so feeding it the union of dealt questions and the
  real answers yields packages containing only genuine (student, their
  question) cells. `R3Q2` codes still resolve through `codeMap`. Verify
  with a test: an allotted quiz’s batch package contains exactly one cell
  per student and the code map round-trips.
- **The package must carry the question text per block** — it already
  prints each question’s stem above its responses, so a reader (human or
  Gemini) sees which question each answer addresses. With one response per
  question block the package gets longer per response; the existing
  `PACKAGE_WORD_BUDGET` splitting handles it.
- **Mark screen** (`/teacher/quiz/[id]/mark`): default to the **by-student**
  view for allotted quizzes (the by-question tabs would each hold one
  student); show the student’s own question stem above their answer strip.
  JumpNav, pencil/ink, phase bolt all unchanged.
- **MARKER-PROJECT.md §1** needs one sentence: packages may contain a
  different question per response; mark each answer against the question
  printed in its own block. (Respect the standing rule: the prompt teaches
  how to judge, the package dictates what — do not enumerate formats.)
- **Reports/analytics**: tag and difficulty analytics already aggregate per
  question answered, so they work; spot-check that nothing divides by “the
  quiz’s question count”.

## 9. `/teacher/new` intake redesign (bundled)

The intake step (step 1 of the wizard, `app/teacher/new/page.tsx` lines
~628–792) is the confusing screen. The later steps — Check & preview,
Settings, Share — are fine and stay as they are.

### 9a. What is wrong

1. **It leads with prose, not a choice.** The first thing on screen is a
   dense blue box: a four-sentence numbered "Workflow" paragraph, a Google
   Forms aside, the tag-vocabulary picker, three buttons, and two expandos.
   It reads as documentation. The teacher's actual first decision — *how do
   I want to add questions?* — is never asked.
2. **The three entry paths are scattered and look unrelated.** Build with
   AI lives at the top; start-from-scratch is a card in the middle; the
   upload/paste tabs sit at the bottom, visually orphaned from the AI
   workflow they complete. Nothing tells you that "Copy AI prompt" (top)
   and "Paste text" (bottom) are steps 1 and 3 of the *same* path.
3. **Advanced concerns interrupt beginners.** Tag vocabulary matters only
   to someone building a multi-quiz analytics practice, yet it sits inside
   the primary box, before any path is chosen. Same for the Type-column
   guide and the Passage explainer.
4. **Everything is the same blue**, so nothing has weight: instructions,
   controls, warnings and asides all compete at equal volume.

### 9b. The redesign — choose a path first, then see only that path

Replace the whole intake step with a **chooser + one expanded path**.
Progressive disclosure; no new routes, no parser changes — this is a
reorganization of what already exists.

**Zone 1 — paper type** (one line, radio-style pills; this is where the
§4a allotted-mode picker lives):

> Same paper for everyone · **Allotted test** — each student gets their own question

**Zone 2 — “How do you want to add questions?”** Three cards, each a
couple of lines, one always expanded (last used, default AI):

1. **✨ Build with AI** — *recommended.* Expanding it shows a compact
   3-step strip, finally making the round-trip legible:
   - **Step 1 — Copy the prompt.** The `Copy AI prompt` button (primary),
     `View prompt` as a quiet text link. Beneath, a single "Options ▸"
     disclosure holding the tag-vocabulary select with its one-line
     explanation — present for the analytics-minded, invisible otherwise.
   - **Step 2 — Chat.** One sentence, not four: "Paste it into ChatGPT,
     Claude or Gemini with your brief and any source material; answer its
     follow-up questions; it returns a quiz file."
   - **Step 3 — Bring back the result.** The paste textarea *and* the
     dropzone, side by side or tabbed, right here inside the card — the
     completion of the path lives next to its beginning.
2. **📄 Upload a file I already have** — the dropzone, with the format
   list (`.xlsx .csv .json .txt .md .gs .js`) and the Google Forms /
   multi-sheet-workbook note as its helper text (that aside finally lands
   where it applies), plus the `Download Excel template` button.
3. **✏️ Start from scratch** — the three type buttons (Multiple choice,
   Written answers, Poll) with their existing one-line explanation
   compressed to a caption.

**Zone 3 — “Format reference”**: one collapsed `details` at the foot of
the page holding the Type-column guide and the Passage/PassageTitle
explainer, both moved verbatim. They are lookup material, not workflow.

### 9c. Copy rules

- The Workflow paragraph dies; its content survives as the three step
  labels in the AI card. Any sentence that explains *another* part of the
  page ("you get an Excel file by default…") moves to the part it
  explains or into Format reference.
- One accent colour for the recommended path only; the other cards stay
  neutral. Warnings keep red; nothing else is blue-on-blue.
- Target: the intake step fits on one laptop screen with all cards
  collapsed, and the teacher's first read is a *question they can answer*
  ("how do you want to add questions?"), not instructions to memorise.

### 9d. Mechanics

State already supports this: `tab` ("upload" | "paste") generalizes to
`path` ("ai" | "upload" | "scratch") with the AI card holding its own
paste/drop toggle. `handleFile`, `handlePaste`, `startFromScratch`,
`copyPrompt`, the preset select and the template download all move
unchanged into their new homes. Remember the last-used path in
`localStorage` so a repeat visit opens the card the teacher actually uses.

## 10. Build order

Each stage leaves the app shippable; nothing student-visible until stage 3.

1. **Foundations** — schema columns, `allotMode` in types, `lib/allot.ts`
   (parser, dealer, coverage) **with tests** (deterministic deal, cycling,
   dedupe, normalization against `normRoll`).
2. **Teacher side** — the `/teacher/new` intake redesign (§9, which now
   *hosts* the paper-type picker), AI-prompt variant, Allotment panel on
   edit, guardrails in validate/routes, quiz-detail badge + coverage
   strip. Doing the redesign first means the allotted mode is born into
   the clean layout instead of being bolted onto the confusing one.
3. **Student side** — public-route gating, two-step start, start/submit/
   result changes, refusal states. Test with a seeded local quiz.
4. **Marking** — mark-page by-student default with per-student stems,
   package round-trip test, MARKER-PROJECT.md sentence, reports
   spot-checks.
5. **Sign-out + polish** — `TeacherBar` everywhere, empty/edge states,
   delete the test quiz, verify on live.

Known frictions to expect (from NEXT-SESSION.md): the local PGlite database
may wedge (move `.data/quizzine` aside); teacher-side verification on live
needs Ritwik signed in — public pages verifiable freely.
